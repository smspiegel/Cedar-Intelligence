# Project Cedar backend MVP

Cedar is a monitor-centric TypeScript service. A tenant-scoped API creates versioned monitors and execution records, Render Workflows runs `runMonitor`, mock connectors normalize observations, SurrealDB stores the audit trail, Agent Memory supplies relevant context, and a structured LLM evaluator emits evidence-citing verdicts. Only the application—not the model—copies the monitor priority onto findings.

## Architecture

`POST /monitors/:id/run` validates the server-controlled tenant and enabled flag, persists a queued execution, then calls Render `startTask("<workflow>/runMonitor", [executionId])`. The task reloads trusted state, runs every source, upserts content-addressed observations, retrieves context, validates the LLM JSON with Zod, writes an evaluation and idempotent findings, then completes the execution. Exceptions—including connector and configured-memory failures—are persisted as failed executions and rethrown for Render retry behavior.

IDs make retries safe: observations hash tenant + monitor + source + external ID + content; findings hash monitor + monitor version + sorted evidence IDs; evaluations hash the execution ID. A changed source item becomes a new observation. An unchanged run succeeds, but cannot create a duplicate finding.

Key modules:

- `src/domain.ts`: Zod domain and API input schemas
- `src/services`: monitor use cases and execution orchestration
- `src/adapters`: SurrealDB, Render, Agent Memory, LLM, and mock-source integrations
- `src/workflow.ts`: real Render Workflow task named `runMonitor`
- `migrations/001_initial.surql`: persistence schema and unique indexes
- `fixtures/mock-observations.json`: matching, nonmatching, duplicate, and changed data (`failure` is generated by the adapter)

## Local setup

Requirements: Node.js 22+, SurrealDB 3.x, and Render CLI 2.12+ for local workflow execution.

```bash
cp .env.example .env
npm install
surreal start --user root --pass root memory
npm run migrate
npm run seed
```

Run the workflow task server in one terminal and the API in another:

```bash
npm run workflow:dev
npm run dev
```

`RENDER_USE_LOCAL_DEV=true` directs the SDK dispatcher to the local task server. Configure `EVALUATOR_URL`, key, and model for a JSON-mode OpenAI-compatible Chat Completions API. For an entirely local test path, use `npm test`; tests inject a deterministic evaluator but exercise the same executor.

In development, API calls require `Authorization: Bearer $API_TOKEN`. Tenant headers and tenant fields in request bodies are ignored; `TENANT_ID` is server configuration. In production, set `AUTH_MODE=jwt`; Cedar validates the configured issuer, audience, and JWKS, then derives the tenant from `AUTH_TENANT_CLAIM`. Do not embed `API_TOKEN` in the Expo bundle.

```bash
curl -H "Authorization: Bearer $API_TOKEN" -H 'content-type: application/json' \
  -d '{"name":"Competitor launch","instructions":"Find Project Birch launches","priority":"P2","enabled":true,"sources":[{"type":"mock","key":"feed","fixture":"matching"}],"memoryScope":"org/demo-org","context":"Toronto matters"}' \
  http://localhost:3000/monitors
```

The original MVP endpoints remain available during migration. New clients should use the versioned API:

- `GET|POST /v1/monitors`, `GET|PATCH /v1/monitors/:id`
- `POST /v1/monitors/:id/executions`, `GET /v1/monitors/:id/executions`
- `GET /v1/executions/:id`
- `GET /v1/findings`, `GET /v1/findings/:id` (includes observation evidence)
- `GET /v1/me`, plus public `GET /health` and `GET /ready`

All versioned collection responses use `{ data, meta }`; internal tenant IDs and monitor snapshots are excluded from their transport DTOs. An execution records an immutable monitor snapshot when dispatched, so edits made after pressing **Run** do not alter that run's audit trail.

## Agent Memory behavior

Set `AGENT_MEMORY_ENDPOINT`, `AGENT_MEMORY_CONTEXT`, and `AGENT_MEMORY_API_KEY` together to enable `@surrealdb/memory`. Cedar calls `AgentMemory.context(query, { k, lens })`. If all three are absent, organization, monitor, and `SEEDED_CONTEXT` text form the explicit development fallback. Partial configuration fails at startup; retrieval errors from a configured service fail the execution and are never converted into empty context.

## Render deployment

The repository-root [`render.yaml`](../render.yaml) defines three independently deployed services: `cedar-web` (Expo static site), `cedar-api` (web service), and `cedar-workflow` (Render Workflow). Each service uses its directory as `rootDir`, so frontend-only changes do not need to rebuild the API.

1. Provision a reachable SurrealDB 3.x instance and configure its connection values on both `cedar-api` and `cedar-workflow`.
2. Configure the JWT issuer, audience, JWKS endpoint, tenant claim, and the web origin allowlist on `cedar-api`.
3. Configure `RENDER_API_KEY` and `RENDER_WORKFLOW_SLUG=cedar-workflow` only on `cedar-api`.
4. Configure the evaluator, Agent Memory, and connector secrets only on `cedar-workflow`.
5. Set `EXPO_PUBLIC_API_URL` to the API's HTTPS URL on `cedar-web`. It is public build-time configuration, never a secret.
6. Deploy the Blueprint. The API's pre-deploy command applies ordered database migrations. Then run a smoke test: `/health` → authenticated `/v1/monitors` → create execution → poll `/v1/executions/:id`.

Render docs: [Workflows](https://render.com/docs/workflows), [TypeScript SDK](https://render.com/docs/workflows-sdk-typescript), and [local development](https://render.com/docs/workflows-local-development). SurrealDB references: [JavaScript SDK](https://surrealdb.com/docs/sdk/javascript) and [Agent Memory JavaScript SDK](https://surrealdb.com/docs/agent-memory/reference/sdk-javascript).

## Scope

This MVP intentionally has one mock connector and one development token. Scheduling, notifications, real social connectors, frontend UI, coverage planning, and AI-generated monitors are excluded.
